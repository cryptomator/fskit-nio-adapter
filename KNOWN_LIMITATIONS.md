# Known limitations

Observed on macOS 27.0.1, 27.2 and 27.2.1 with JDK 26.

- Another account gets "Permission denied" on a mounted volume, but root reads and changes it like the user who mounted it. An account that can get to the mount point is not kept from everything:
  - It can enter the volume's root and a directory the mounting user has accessed, though not list them. While it stays there, the volume can only be unmounted by force.
  - For an entry the mounting user has accessed, `stat` answers with the entry's attributes, such as its size, from the kernel's cache.
  - While the mounting user holds a file open, the account can read it, and while the mounting user holds it open for writing, it can also write to it. macOS passes on an open of a file that is already open only if it asks for more access than the file is open with, or once a change outside made the volume drop what macOS cached of the file. Only this way of handling opens lets the volume show changes made outside it.
  - Removing such an entry reports success, although nothing is removed.
  - Extended attribute calls by path on such an entry are not refused. They reveal nothing, and what they set is discarded.
  - An FSEvents stream on the mount point reports the paths of entries as they change.
  - For a symbolic link the mounting user has read, listed with `ls -l` or followed, `readlink` answers with the target from the kernel's cache. `cp -P` copies such a link, reports that it could not copy the extended attributes and exits with status 1. Reading a file of the volume through the link is still refused.

  A mount point below a directory the other account cannot enter keeps all of this from it. A volume mounted without a mount point is in `/Volumes`, which every account can enter.
- Finder's Trash creates `.Trashes` in the volume root, which appears in the mounted `Path`.
- The name `.fseventsd` in the volume root is taken. The volume shows a directory of that name with an empty file `no_log` in it, which keeps macOS from creating the directory in the mounted `Path` and storing its log of file system events there. Neither is stored or can be changed, and the root's listing leaves the directory out. An entry named `.fseventsd` that the mounted `Path` already holds cannot be reached through the volume and stays as it is. Without that log, macOS has no event history for the volume, and an FSEvents stream created relative to the device reports absolute paths. Events are still delivered as they happen.
- AppleDouble files (`._<name>`) and `.DS_Store` are hidden, as the macFUSE provider hides them with its `noappledouble` option. Such entries in the mounted `Path` cannot be reached through the volume, and listings leave them out. Creating one, or renaming an entry to such a name, fails with "Operation not permitted". Removing a directory, or replacing one by a rename, deletes the hidden files in it when it holds nothing else. A directory that holds a hidden directory cannot be removed through the volume ("Directory not empty"). If every entry of such a plain directory starts with `._`, macOS deletes the `._` files before it refuses, as it does without the volume.
- Hard links cannot be created: `ln` fails with "Operation not supported".
- macOS follows a symbolic link itself. A relative target leads to an entry of the volume, an absolute one into the Mac's own file system and not into the mounted `Path`.
- A symbolic link created on the volume has its target without a trailing slash and without doubled slashes: `ln -s dir/ name` stores `dir`. A vault also stores the target in composed Unicode form.
- A symbolic link whose target is longer than 1023 bytes cannot be read or followed: `readlink` and `cat` fail with "File name too long", `ls -l` lists it without a target, and Finder shows it with a question mark. A vault can hold such a link, but none can be created on the volume.
- A change to the mode or the times of a symbolic link reports success and has no effect (`chmod -h`, `touch -h`).
- A symbolic link whose target is not valid UTF-8, which a plain directory can hold, is shown with the invalid bytes replaced by `�`, so it leads elsewhere or nowhere.
- Extended attributes are accepted and not stored: `xattr -w` succeeds, and the attribute is gone. A file copied or saved to the volume loses its Finder tags, its resource fork and its quarantine flag, which marks a download for the check macOS runs before opening it.
- An extended attribute or resource fork from 256 KiB up to at least 1 MiB is refused with "File too large". `cp` then copies the data, reports that it could not copy the extended attributes and exits with status 1, while Finder copies such a file without complaint. One of 2 MiB or more is accepted.
- Work on many small files takes longer than through macFUSE. On a vault, creating 5,000 files takes five times as long, a first `ls -l` of them four and a half times, removing them four times, and reading them three times. Every request that reaches the JVM is a round trip through the extension, which takes about 0.15 ms. macOS sends more requests than an operation needs: `ls -l` looks up every entry again after listing it. Large files are read at least as fast as through macFUSE: two parallel readers of 512 MiB each take 0.58 s on a vault, against 0.74 s through macFUSE.
- On a plain directory, creating an entry or looking one up by name for the first time takes longer the more entries its directory holds, because the JDK lists that directory to find the name as it is stored. With 5,000 files in one directory, creating them takes 14 s and `ls -l` 9 s, against 8 s and 2 s on a vault.
- A FIFO or a socket in the mounted `Path` is shown as a regular file. Opening the socket fails with "Input/output error". Opening the FIFO waits until a process opens it for writing in the mounted `Path` itself, not through the volume. Removing the FIFO or renaming a directory above it waits for that writer as well. The rest of the volume stays usable meanwhile.
- `rm` of a name that another process renames at the same moment can report success although nothing is removed: the entry keeps its new name.
- A listing in progress holds the names its directory had when the listing started. An entry created or renamed in the directory meanwhile is missing from it under its new name, and one removed meanwhile is left out.
- The JVM keeps the names of listed directories in memory, within a sixteenth of its heap per volume, and beyond that drops the listings used least recently. On a vault, a directory of 200,000 files with names of 26 characters fits into the share of a 512 MiB heap: its names take about 17 MiB, and listing it took up to 53 MiB of that heap. A directory whose names exceed that share is kept while it is listed and read again whenever a caller returns to it after listing another directory.
- When a listing was dropped and its directory holds other names by the time the listing continues, the continuation fails with "Input/output error". `find` and `cp -R` print nothing for a failed listing and leave out the rest of that directory. A tool that removes entries while it walks a tree can meet this in a directory whose names exceed the share of the heap for listings. On a vault served with that share cut down, `bfs -delete` left such a directory half removed. `/usr/bin/find -delete` and `rm -rf` removed it.
- When several processes walk the same tree of a volume at once, macOS now and then ends one of their listings early without an error. The adapter is not asked for the entries left out. On a vault, six `/usr/bin/find` walked a tree of 40 directories with 200 files each at the same time. In 9 of 1,068 such walks, a `find` missed the last five entries of one directory and exited with status 0.
- FSKit tells a volume nothing about changes made to its files elsewhere, and keeps what it has read of a file or folder (Apple r.177724575). The adapter therefore watches the mounted `Path`, or the directory of a vault, through FSEvents and makes macOS read a changed file or folder again. This needs the library `FSKitNioSupport` that the jar carries on macOS:
  - A file that another process, such as a sync client, changes in the mounted `Path` shows its new size and content within about a second. Without the library it does so only once its folder is listed, or after an open of it failed as described below. A Finder window open on the folder keeps showing the old size until it is opened again.
  - A file that a process holds open while it changes keeps showing that process what it has read of the old version until the last descriptor is closed. What it has not read yet comes from the file as it is now. After a change in place on a plain directory, that is the new version, so the process can see parts of both. Opening it again meanwhile fails with "Stale NFS file handle" on a plain directory and shows the old version on a vault. After the last close, the next access shows the new version, on a vault a few milliseconds later.
  - The open that finds a file changed fails with "Stale NFS file handle", whether for reading or for writing. The next open shows the new version.
  - A change that replaces a file is kept while a process holds the file open for writing, on a vault as well. A change made in place to a file in a plain directory can be overwritten in part by what such a process wrote before it.
  - On macOS 27.2.1 and later, an entry that another process creates, removes or renames in a folder below the root of the mounted `Path` shows within half a second on a plain directory and on a vault, also under a name that macOS looked up while no entry had it. macOS then looks up again the names it knew in that folder, though not those in the folders below it. Without the library, this happens once a listing of the parent folder shows the folder changed. An open Finder window shows the change only once it is opened again.
  - Directly in the volume's root, and in every folder on macOS 27.0.x, a file removed outside still answers `stat` with its old attributes until it is opened. The open fails with "No such file or directory", and `stat` finds no file from then on. A name that macOS looked up while no entry had it stays missing until macOS drops the folder from its cache, also after something else created an entry under that name. macOS refuses to drop what it cached of the root. 27.1 and 27.2 were not checked.
  - A file replaced by one of the same size and modification time is not noticed, nor one replaced by one of the same size while a process writes to it. A change to the names in a folder that leaves the folder's size and modification time as they were is not noticed either, as when a sync tool renames an entry and then restores the folder's time.
  - A file that another process removes from a folder just before the volume itself creates, removes or renames an entry there keeps answering `stat` with its old attributes. That lasts until it is opened, which fails with "No such file or directory", or until a later change outside the volume makes macOS drop the names it cached in that folder.
  - Replacing a directory of the mounted `Path` with a file or a link from outside, while it is mounted, is not supported.
- The mounted `Path` must not hold two names that differ only in Unicode normalization.
- The volume is case-sensitive: on a case-insensitive backing store, a name that differs from an existing one only in case is reported as absent and cannot be created.
- A time or permission change on a removed file that is still open is ignored.
- A modification or access time cannot be set on a file or directory whose owner may not read it: `touch` fails with "Permission denied", because the JDK opens the entry for reading to set its times.
- One request can change several attributes, as `setattrlist` does. When the backing store refuses one of them after another has been applied, the request still succeeds, and only the JVM's log reports the refusal.
- A file or directory is created even when the backing store refuses to set its mode. It then keeps the mode it was created with, which the umask of the JVM may have cut down. Only the JVM's log reports the refusal.
- A modification or access time later than 11 April 2262, 23:47:16 UTC, is set to that time, the latest the JDK sets.
- A rename that replaces an existing entry is atomic only when a file replaces a file. With a directory or a symbolic link on either side, the target is removed first and is gone if the move then fails.
- A file that was opened for writing only and then loses its owner-write permission cannot be opened for reading until it is closed.
- A volume mounted without a mount point, in `/Volumes`, is unmounted through the provider or with `diskutil unmount`. `umount` answers "Operation not permitted" to the user who mounted it.
- A volume mounted without a mount point gets a mount point named after it in ASCII: `Tresor Müller` is mounted at `/Volumes/Tresor Muller`. A character without an ASCII form, and `/`, becomes `_`. Finder shows the name unchanged.
- A mount does not survive its JVM. When the JVM dies, operations on the volume fail with an I/O error at once. `umount -f` removes the mount, and `diskutil unmount force` removes one in `/Volumes`. The directory holding the manifest stays in the temp directory.
- A mount does not survive its extension process either. When the process dies, macOS removes the mount at once, and an operation in flight fails with "Device not configured". A mount point the application chose is a plain directory again, so whatever is written to it afterwards lands in that directory, not in the mounted `Path`. A mount point in `/Volumes` is removed together with the mount. `Mount#whenTerminated()` completes, so the application learns of it.
- `Mount#whenTerminated()` completes only once every operation still running on the mounted `Path` has returned, whatever ended the mount. An operation that hangs holds it back.
- On macOS 27 or later with an `aarch64` JVM, the provider is offered whether or not macOS has registered an extension for its file system type. Inside an app, it is offered only if the app embeds such an extension. Where no extension serves the type, `mount()` fails with `MountFailedException`.
